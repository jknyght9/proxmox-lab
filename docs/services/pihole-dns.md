# Pi-hole DNS

Pi-hole provides DNS resolution, ad-blocking, and local hostname records for all lab services. It runs as Proxmox LXC containers (one per Proxmox cluster node) and is managed by the `lxc-pihole` Terraform module.

## Overview

| Property | Value |
|----------|-------|
| **Type** | Proxmox LXC container |
| **VMIDs** | 910, 911, 912 (one per Proxmox node) |
| **OS** | Debian 12 |
| **Pi-hole version** | v6 (FTL engine, TOML config) |
| **DNS upstream** | Unbound (DNS-over-TLS to Cloudflare/Quad9) |
| **Replication** | Gravity Sync (dns-01 is primary) |
| **Ports** | 53 (DNS), 80 (HTTP admin) |

## Architecture

```
Client DNS query
    |
    v
Pi-hole (ad-block filter, local records)
    |
    |-- local record (*.dns-suffix) --> return IP
    |-- blocked domain              --> return 0.0.0.0
    |-- external query
            v
         Unbound (DNSSEC validation, DNS-over-TLS)
            |
            v
         Cloudflare 1.1.1.1 or Quad9 9.9.9.9 (TLS port 853)
```

## DNS Cluster

The number of Pi-hole nodes scales with the Proxmox cluster:
- 1 Proxmox node: 1 Pi-hole (dns-01)
- 2 Proxmox nodes: 2 Pi-holes (dns-01, dns-02)
- 3 Proxmox nodes: 3 Pi-holes (dns-01, dns-02, dns-03)

Nodes are configured in `terraform.tfvars` under `dns_main_nodes`:

```hcl
dns_main_nodes = [
  { hostname = "dns-01", ip = "192.168.1.4/24", gw = "192.168.1.1", target_node = "pve1" },
  { hostname = "dns-02", ip = "192.168.1.5/24", gw = "192.168.1.1", target_node = "pve2" },
  { hostname = "dns-03", ip = "192.168.1.6/24", gw = "192.168.1.1", target_node = "pve3" },
]
```

## Gravity Sync

Gravity Sync replicates Pi-hole configuration from the primary (dns-01) to all secondary nodes:

- **Primary**: dns-01 (Gravity Sync source)
- **Secondaries**: dns-02, dns-03 (sync from primary)
- **Sync interval**: 5 minutes (cron job)
- **What replicates**: Gravity database, custom DNS records, block lists, allow lists

To force a sync immediately:

```bash
ssh labadmin@dns-01 "sudo gravity sync push"
ssh labadmin@dns-02 "sudo gravity sync pull"
```

## Pi-hole v6 Configuration

Pi-hole v6 uses a TOML configuration file at `/etc/pihole/pihole.toml`. The FTL engine replaces the older dnsmasq-based setup.

!!! warning "Pi-hole v6 API change"
    Pi-hole v6 uses a new REST API at `/api/`. The old PHP API from Pi-hole v5 is not available. The Terraform `ryanwholey/pihole` provider is incompatible with v6. DNS records are managed via `pihole-FTL --config` CLI and SSH null_resource provisioners instead.

Custom local DNS records are stored in the `dns.hosts` array in `pihole.toml` and managed by the Layer 2 `dns-records.tf` Terraform resource.

## Local DNS Records

Layer 2 Terraform creates all service DNS records in Pi-hole via SSH:

```bash
# Records are added using pihole-FTL CLI:
pihole-FTL --config dns.hosts[0]="192.168.1.50 nomad01.mylab.lan"
pihole-FTL --config dns.hosts[1]="192.168.1.50 vault.mylab.lan"
# ...etc
```

To rebuild all DNS records without a full redeploy:

```bash
./setup.sh --dev
# d11) Rebuild DNS records
```

## Unbound Configuration

Each Pi-hole node runs Unbound as a DNS resolver for external queries. Unbound configuration is stored in the `lxc-pihole` module at `terraform/lxc-pihole/files/unbound.conf`.

Key settings:
- **DNS-over-TLS**: Queries forwarded to Cloudflare (`1.1.1.1@853`) and Quad9 (`9.9.9.9@853`) over TLS
- **DNSSEC**: Enabled for validation
- **Prefetching**: Enabled to reduce latency on popular domains

## High Availability

When `ha_dns_enabled: true` is configured in `bootstrap.yml`, keepalived VRRP provides a Virtual IP (VIP) that floats between Pi-hole nodes:

```
<dns-ha-vip>  --> dns-01 (priority 101, MASTER)
               if dns-01 fails --> dns-02 (priority 100)
               if dns-02 fails --> dns-03 (priority 99)
```

Clients configure only the VIP as their DNS server. Failover is automatic when the master Pi-hole's DNS check fails.

Required: `ha_dns_vrrp_router_id` must not conflict with any other VRRP on your network. Requires `privileged = true` on the LXC containers (for NET_ADMIN capability).

## Accessing Pi-hole Admin

Via DNS (through Traefik):
```
https://pihole.<dns-suffix>
```

Direct access:
```
http://<dns-01-ip>/admin
```

!!! info "Authentik forward auth"
    Pi-hole is protected by Authentik forward auth when accessed through Traefik. Direct access via IP bypasses authentication.

## Passwords

Pi-hole admin and root passwords are randomly generated by Terraform and stored in Vault at `secret/pihole`:

```bash
# View the Pi-hole admin password
vault kv get -field=admin_password secret/pihole
```

## Troubleshooting

### DNS not resolving after deployment

1. Check that your client is using the Pi-hole IP (or HA VIP) as its DNS server
2. Test DNS resolution directly from Pi-hole: `dig @<dns-01-ip> google.com`
3. Check Pi-hole FTL status: `ssh labadmin@dns-01 "systemctl status pihole-FTL"`
4. View FTL logs: `ssh labadmin@dns-01 "journalctl -u pihole-FTL -f"`

### Local hostnames not resolving

1. Check DNS records exist in Pi-hole: Browse to `/admin/dns-records`
2. Force rebuild: `./setup.sh --dev` then `d11) Rebuild DNS records`
3. Verify the record: `dig @<dns-01-ip> vault.<dns-suffix>`

### Gravity Sync not working

1. Check SSH connectivity between nodes:
   ```bash
   ssh labadmin@dns-01 "ssh -i /etc/gravity-sync/gravity-sync.rsa dns-02 echo ok"
   ```
2. Run manual sync: `ssh labadmin@dns-01 "sudo gravity sync push"`
3. Check sync logs: `ssh labadmin@dns-01 "sudo gravity sync logs"`

### Container provisioning fails during apt-get

The `bootstrap_dns` setting controls which DNS server LXC containers use during provisioning. If your network blocks external DNS (1.1.1.1, etc.), set `bootstrap_dns` to your gateway IP:

```hcl
# terraform/terraform.tfvars
bootstrap_dns = "<gateway-ip>"
```

This is auto-populated from the `network.gateway` in `bootstrap.yml` during bootstrap.
